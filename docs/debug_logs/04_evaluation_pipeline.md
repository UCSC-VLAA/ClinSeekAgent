## 1. High-Level Pipeline Overview

```
deploy_agent.py main()
  ├── Load query data (JSON/JSONL with subject_id, task, prediction_time, label)
  ├── Initialize generator (BedrockAsyncGenerator or VLLMOpenAIAsyncGenerator)
  ├── Initialize BrowserPool (local HTTP or Serper API)
  ├── Initialize EHRToolPool (HTTP client to MCP server)
  └── For each query:
       └── run_one_native(question, qid, generator, browser_pool, ehr_pool)
            ├── Build messages: [system_prompt, user_question]
            ├── Parse all 23 tool schemas (3 browser + 20 EHR)
            └── Loop (up to max_rounds=200):
                 ├── generator.chat_completion(messages, tools, tool_choice="auto")
                 ├── Extract tool_calls from response
                 ├── For each tool_call:
                 │    ├── normalize_tool_call_name(raw_name)
                 │    ├── Route by prefix:
                 │    │    ├── "ehr.*" → EHRToolPool.call_tool() → MCP server (JSON-RPC)
                 │    │    └── "browser.*" → BrowserPool.call_tool() → search/scrape backend
                 │    └── Append {"role": "tool", "content": result} to messages
                 └── Break if ehr.finish is called
```

**Key files:**

| File | Role |
|------|------|
| `deploy_agent.py` | Entry point and agent loop orchestrator |
| `data_utils.py` | Task prompt templates, system prompts, tool schema definitions |
| `bedrock_generator.py` | AWS Bedrock Claude backend (Anthropic Messages API) |
| `vllm_generator.py` | vLLM OpenAI-compatible backend with multi-format tool call parsing |
| `ehr_pool.py` | HTTP client for MCP server (EHR tools) |
| `browser.py` | Browser tool backends (local HTTP service or Serper API) |

## 2. Task Prompt Construction

### 2.1 Data Loading

`deploy_agent.py` loads JSON/JSONL files where each record contains:

```json
{
    "subject_id": 10000032,
    "prediction_time": "2150-12-01 10:00:00",
    "task": "diagnoses_ccs",
    "label": [{"name": "..."}]
}
```

The question is generated by `resolve_question()` (line 199), which calls `generate_question_from_task()` from `data_utils.py`:

```python
# data_utils.py:116-136
def generate_question_from_task(task_data):
    task_type = task_data.get("task", "diagnoses_ccs")
    template = TASK_PROMPT_TEMPLATES.get(task_type)
    question = template.format(
        current_time=task_data["prediction_time"],
        subject_id=task_data["subject_id"]
    )
    return question
```

### 2.2 Task Prompt Templates

Each task type has a template in `TASK_PROMPT_TEMPLATES` (`data_utils.py`, line 8). For example, `diagnoses_ccs`:

```
<task_instruction>
Your current task is to act as a diagnostician.

Your objective is to determine all plausible diagnoses for the patient's current
condition by analyzing the patient's complete history.

You must find the most likely official CCS candidates using the
**`diagnoses_ccs_candidates`** reference table.

When you need medical knowledge or clinical information to support your diagnostic
reasoning, use the `browser.search` tool to find authoritative medical information
from reliable sources.

Present your final answer as a **list format** with `finish` tool calling, which
must contain **multiple plausible diagnoses**. Each item in the list must be a string
representing an official CCS diagnosis name, and **must not contain any codes or
other additional information**.
</task_instruction>

<patient_info>
Current Time: 2150-12-01 10:00:00
Patient Subject ID: 10000032
</patient_info>
```

Note: compared to the main AgentEHR pipeline, these templates explicitly mention `browser.search` as a tool for gathering medical knowledge.

## 3. Tool Definitions: How the LLM Knows Which Tools Exist

### 3.1 Static JSON Tool Schemas

Unlike the main AgentEHR pipeline (which dynamically discovers tools from the MCP server), OpenResearcher defines all tool schemas **statically as JSON strings** in `data_utils.py`.

Tools are loaded at line 467 of `deploy_agent.py`:

```python
tools = json.loads(COMBINED_TOOL_CONTENT_FULL)
```

Where `COMBINED_TOOL_CONTENT_FULL` is built by:

```python
# data_utils.py:867-874
def get_combined_tools_with_all_ehr():

    ehr_tools = json.loads(EHR_TOOL_CONTENT_JSON)       # 20 EHR tools
    return browser_tools + ehr_tools

COMBINED_TOOL_CONTENT_FULL = json.dumps(get_combined_tools_with_all_ehr())
```

## 4. System Prompt: How the LLM Is Instructed to Call Tools

The system prompt is `DEVELOPER_CONTENT_CLAUDE` (`data_utils.py`, line 152). It serves two purposes: (1) describe available tool categories and (2) specify the exact tool call format.

```
You are a research assistant with access to both web browsing and clinical EHR tools.

**Browser Tools** (for web research and medical knowledge):
- browser.search: Search the web for information, medical knowledge, clinical guidelines
- browser.open: Open and read web pages
- browser.find: Find text within pages

**EHR Tools** (for clinical data analysis):
- ehr.load_ehr: Load patient EHR database (must be called first for clinical tasks)
- ehr.get_table_names: List available patient data tables
- ehr.get_column_names: Get table column information
- ehr.get_records_by_time: Query patient records within time range
- ehr.run_sql_query: Execute SQL queries on patient database
- ehr.get_candidates_by_semantic_similarity: Search medical terminology/diagnosis codes
- ehr.get_candidates_by_keyword: Search diagnosis codes by keyword
- ehr.think: Record your reasoning process
- ehr.finish: Submit your final answer

**Important:** Whenever you engage in thinking, reasoning, or analysis, you MUST use
Browser Tools to support your process, including assisting with information retrieval
and verification. Do NOT rely solely on internal knowledge.

**Tool Call Format Requirement:** Whenever you call a tool, you MUST emit the tool call
in exactly this plain-text format:
`[Tool Call: {function_name}({arguments})]`

Formatting rules for tool calls:
- Use exactly the prefix `[Tool Call:`
- `function_name` must be the full tool name such as `ehr.load_ehr`,
  `ehr.get_records_by_time`, `browser.search`, or `ehr.finish`
- `{arguments}` must be a valid JSON object
- Do not use XML tool-call formats
- Do not use raw JSON arrays or other wrapper formats for tool calls
- If you need to call multiple tools in one response, emit one `[Tool Call: ...]`
  entry per tool
- When you have enough information to answer, you must call `ehr.finish` using
  this same format

Your final response should be submitted by calling `ehr.finish` in the required
`[Tool Call: ...]` format.
```

**Key points:**
- The system prompt explicitly instructs the model to use `[Tool Call: name(args)]` bracket format. This is especially important for the **vLLM backend**, where models may not natively support structured tool calling and the pipeline must parse tool calls from the model's text output.
- For the **Bedrock backend**, the native Anthropic tool-calling API handles structured tool calls automatically, so this text instruction serves as a fallback/reinforcement.

## 5. Sending the Request to the LLM

### 5.1 The Agent Loop Call

In `run_one_native()` (`deploy_agent.py`, line 483):

```python
response = await generator.chat_completion(
    messages=messages,
    tools=tools,          # All 23 tool schemas
    tool_choice="auto",   # Let model decide
    temperature=temperature,
    max_tokens=8192
)
```

Both backends implement `chat_completion()` with the same interface but differ internally.

### 5.2 Bedrock Backend

`bedrock_generator.py` `chat_completion()` (line 330):

1. **Convert messages** from OpenAI format to Anthropic format via `_convert_messages_to_anthropic()`:
   - `system` messages → extracted as a separate `system` parameter
   - `assistant` messages with `tool_calls` → converted to `tool_use` content blocks
   - `tool` messages → converted to `tool_result` content blocks in a `user` message
   - Consecutive same-role messages are merged (Anthropic requires alternating roles)

2. **Convert tools** via `_convert_tools_to_anthropic()`:
   - **Critical**: Bedrock requires tool names matching `^[a-zA-Z0-9_-]{1,128}$`, so dots are replaced with underscores: `browser.search` → `browser_search`, `ehr.load_ehr` → `ehr_load_ehr`
   - `"parameters"` key is renamed to `"input_schema"`

3. **Call Bedrock API**:
   ```python
   request = {
       "anthropic_version": "bedrock-2023-05-31",
       "max_tokens": max_tokens,
       "temperature": temperature,
       "messages": anthropic_messages,
       "system": system_prompt,
       "tools": anthropic_tools,
       "tool_choice": {"type": "auto"}
   }
   response = self.client.invoke_model(modelId=self.model_id, body=json.dumps(request))
   ```

4. **Convert response** back to OpenAI format via `_convert_response_to_openai()`:
   - `tool_use` content blocks → `tool_calls` array
   - Underscored names converted back to dotted: `browser_search` → `browser.search`
   - `stop_reason: "tool_use"` → `finish_reason: "tool_calls"`

### 5.3 vLLM Backend

`vllm_generator.py` `chat_completion()` (line 763):

1. **Prepare messages** via `_prepare_messages()`:
   - This is a fundamentally different approach from Bedrock. Since many local models don't natively support the OpenAI tool-calling protocol, messages are **flattened into plain text**:
     - Assistant messages with `tool_calls` are rendered as text: `[Tool Call: browser.search({"query": "..."})]`
     - `tool` role messages are converted to `user` role with a `[Tool Response]` prefix
     - Consecutive same-role messages are merged
   - The model sees tool calls and results as plain text in the conversation, not as structured API objects.

2. **Call vLLM API** (OpenAI-compatible):
   ```python
   response = self._make_client().chat.completions.create(
       model=model_name,
       messages=prepared_messages,
       tools=tools,             # Still passed for models that support it natively
       tool_choice=tool_choice,
       max_tokens=max_tokens,
       extra_body=extra_body,   # e.g., enable_thinking for Qwen3
   )
   ```

3. **Convert and parse response** via `_convert_response_to_openai()` -- this is where the multi-format fallback parsing happens (see Section 6).

## 6. Parsing the LLM Response

### 6.1 Bedrock: Direct Structured Parsing

Bedrock responses contain native `tool_use` blocks. The conversion in `_convert_response_to_openai()` (`bedrock_generator.py`, line 257) is straightforward:

```python
for block in content_blocks:
    if block.get("type") == "text":
        text_content += block.get("text", "")
    elif block.get("type") == "tool_use":
        # Restore dotted names: "browser_search" → "browser.search"
        raw_name = block.get("name", "")
        if raw_name.startswith("browser_"):
            raw_name = "browser." + raw_name[len("browser_"):]
        tool_calls.append({
            "id": block.get("id", "1"),
            "type": "function",
            "function": {
                "name": raw_name,
                "arguments": json.dumps(block.get("input", {}))
            }
        })
```

### 6.2 vLLM: Multi-Format Fallback Chain

This is the most complex part. The `_convert_response_to_openai()` method (`vllm_generator.py`, line 637) tries **8 extraction strategies** in order, stopping at the first one that finds tool calls:

```
1. Native API tool_calls (from response.choices[0].message.tool_calls)
   ↓ (if empty)
2. XML blocks in content:        <tool_call>{"name": "...", ...}</tool_call>
   ↓ (if empty)
3. Naked XML in content:         <function=browser.search><parameter=query>...</parameter></function>
   ↓ (if empty)
4. Inline function in content:   <function=browser.search({"query": "..."})>
   ↓ (if empty)
5. XML blocks in reasoning_content        (same as #2, searched in thinking output)
   ↓ (if empty)
6. Naked XML in reasoning_content         (same as #3)
   ↓ (if empty)
7. Inline function in reasoning_content   (same as #4)
   ↓ (if empty)
8. Bracket format in content:    [Tool Call: browser.search({"query": "..."})]
   ↓ (if empty)
9. Bracket format in reasoning_content    (same as #8)
```

#### Strategy 1: Native API `tool_calls`

```python
for tool_call in getattr(message, "tool_calls", None) or []:
    tool_calls.append({
        "id": tool_call.id,
        "type": "function",
        "function": {
            "name": _normalize_tool_name(tool_call.function.name),
            "arguments": arguments,
        },
    })
```

#### Strategy 2: XML `<tool_call>` blocks (`_extract_xml_tool_calls`)

Parses `<tool_call>...</tool_call>` blocks. The inner content can be either:
- JSON: `<tool_call>{"name": "browser.search", "arguments": {"query": "..."}}</tool_call>`
- XML parameters: `<tool_call><function=name><parameter=key>value</parameter></function></tool_call>`

#### Strategy 3: Naked XML function calls (`_extract_naked_xml_function_calls`)

Parses `<function=name>...<parameter=key>value</parameter>...</function>` without `<tool_call>` wrapper.

#### Strategy 4: Inline function calls (`_extract_inline_function_calls`)

Parses `<function=browser.search({"query": "..."})>` -- function name with arguments directly in parentheses.

#### Strategy 8: Bracket format (`_extract_bracket_tool_calls`)

Parses `[Tool Call: function_name({"arg": "value"})]`. This is the format explicitly requested in the system prompt.

The regex-free parser handles nested parentheses and quoted strings correctly:

```python
# vllm_generator.py:413-518
# Finds "[Tool Call:" prefix, extracts function name up to "(", then
# tracks parenthesis depth with string escaping to find matching ")",
# then looks for closing "]"
```

### 6.3 Tool Name Normalization

Both backends normalize raw tool names via `normalize_tool_call_name()` (`deploy_agent.py`, line 97):

```python
def normalize_tool_call_name(function_name: str) -> str:
    name = (function_name or "").strip()
    # browser.search → browser.search (already correct)
    if name.startswith("browser."):  return name
    # browser_search → browser.search (Bedrock underscore format)
    if name.startswith("browser_"):  return f"browser.{name[8:]}"
    # search / open / find → browser.search / browser.open / browser.find
    if name in {"search", "open", "find"}:  return f"browser.{name}"
    # ehr.load_ehr / ehr_load_ehr → kept as-is (handled later)
    if name.startswith("ehr.") or name.startswith("ehr_"):  return name
    # bare name like "load_ehr" → ehr_load_ehr
    if "." not in name:  return f"ehr_{name}"
    return name
```

### 6.4 Handling Missing Tool Calls

If the model response contains no tool calls, the pipeline sends a retry reminder (`deploy_agent.py`, line 520):

```python
if not tool_calls:
    finish_reminders_sent += 1
    if finish_reminders_sent > MAX_TOOLLESS_REMINDERS:  # 3
        break
    messages.append({
        "role": "user",
        "content": "Your previous response did not include an actual tool call.\n"
                   "In your next response, you MUST emit at least one tool call in exactly "
                   "this format: `[Tool Call: {function_name}({arguments})]`.\n..."
    })
```

## 7. Tool Routing and Execution

### 7.1 Prefix-Based Routing

After parsing, each tool call is routed by namespace prefix (`deploy_agent.py`, line 578):

```python
for tool_call in tool_calls:
    function_name = normalize_tool_call_name(raw_function_name)
    function_args = json.loads(function_args_raw)

    # Sanitize EHR tool arguments (fix subject_id, timestamp, year issues)
    function_args, _ = sanitize_ehr_tool_args(function_name, function_args, patient_context)

    if function_name.startswith("ehr.") or function_name.startswith("ehr_"):
        # Strip prefix: "ehr.get_table_names" → "get_table_names"
        actual_function_name = function_name.replace("ehr_", "").replace("ehr.", "")
        result = await ehr_pool.call_tool(qid, actual_function_name, function_args)

    elif function_name.startswith("browser."):
        # Strip prefix: "browser.search" → "search"
        actual_function_name = function_name.split(".", 1)[1]
        result = await browser_pool.call_tool(qid, actual_function_name, function_args)
```

### 7.2 EHR Tool Execution (`ehr_pool.py`)

`EHRToolPool` communicates with the MCP server via HTTP using **JSON-RPC 2.0**:

**Session initialization** (`_init_mcp_session`, line 41):
1. POST `{"method": "initialize", "params": {"protocolVersion": "2024-11-05", "clientInfo": {...}}}` to MCP URL
2. Extract `mcp-session-id` from response headers
3. POST `{"method": "notifications/initialized"}` with session header to activate the session

**Tool execution** (`_call_mcp_tool`, line 138):
```python
payload = {
    "jsonrpc": "2.0",
    "id": 1,
    "method": "tools/call",
    "params": {
        "name": tool_name,        # e.g., "get_records_by_time"
        "arguments": tool_args     # e.g., {"subject_id": "10000032", ...}
    }
}
response = await self.client.post(self.mcp_url, json=payload, headers=headers)
```

The response is parsed from either SSE format (`data: {json}`) or plain JSON, then the tool result text is extracted from `result.content[].text`.

**Smart retry** (line 258): If a tool fails with "Please call load_ehr first" or "No tables found", the pool automatically re-calls `load_ehr` with the stored arguments and retries the original tool call.

### 7.3 Browser Tool Execution (`browser.py`)

`BrowserPool.call_tool()` (`deploy_agent.py`, line 320):

1. Wraps tool arguments in an **OpenAI Harmony `Message`** with `recipient` set to `browser.search`, `browser.open`, or `browser.find`
2. Calls `BrowserTool._process(message)` which dispatches to `self.search()`, `self.open()`, or `self.find()`
3. Extracts text content from the returned Harmony messages

**Browser backends:**

- **`LocalServiceBrowserBackend`** (`browser.py`, line 107): Calls a local HTTP service
  - `search(query, topn)` → `POST {base_url}/search` → returns HTML with search results → processed via `process_html()`
  - `fetch(url)` → `POST {base_url}/get_content` → returns page HTML → processed via `process_html()`

- **`SerperServiceBrowserBackend`** (`browser.py`, line 218): Calls the Serper cloud API
  - `search(query, topn)` → `POST https://google.serper.dev/search` with `X-API-KEY` header
  - `fetch(url)` → `POST https://scrape.serper.dev/` with `X-API-KEY` header

### 7.4 Argument Sanitization

Before EHR tool execution, `sanitize_ehr_tool_args()` (`deploy_agent.py`, line 269) fixes common LLM mistakes:
- For `ehr.load_ehr`: overwrites `subject_id` and `timestamp` with values parsed from the question (prevents hallucinated patient IDs)
- For `ehr.get_records_by_time`: fixes `end_time` year when the patient lives in the future (year >= 2100) but the model uses a real-world year

### 7.5 Tool Result Message

After execution, the result is appended to the conversation:

```python
# deploy_agent.py:600-604
messages.append({
    "role": "tool",
    "tool_call_id": tool_id,
    "content": result          # Plain text string
})
```

## 9. LLM Backend Differences: Bedrock vs vLLM

| Aspect | Bedrock (`bedrock_generator.py`) | vLLM (`vllm_generator.py`) |
|--------|------|------|
| **API protocol** | Anthropic Messages API via `boto3 invoke_model` | OpenAI-compatible `/v1/chat/completions` |
